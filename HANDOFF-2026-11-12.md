## 1. One-paragraph verdict

The flash-safety guarantees — only slot-B boot images and userdata, never
bootloader/radio/devinfo/persist/calibration, slot A preserved — hold under
adversarial review, in code and in mock execution. The defense is layered:
an allowlisted write gate in every writer (installer, fastboot tool, ssh
push, on-phone kernel-update hook), a data-not-code descriptor parser in
every consumer, an on-phone initramfs guard that removes whole-disk nodes
and `--setro`s everything else, dead-man switches with fallback to slot A,
and a signed-bundle integrity chain (GPG fingerprint pins → checksums →
manifest-as-data whose install plan must equal the descriptor's). Eight
findings, none High/Critical; two have prepared fixes (draft PRs on the
fork); the rest are hardening. What remains untested needs a Pixel 7 Pro.

## 3. The safety model, as verified in code

Layer 1 — **writers are gated.** `tools/install-phone` `flash()` (line
~640): a partition is writable only if it is `${p}_b` for a descriptor
`BOOT_IMAGES` entry **and** on the descriptor's `UFS_RW`; `userdata` must
be on `UFS_RW` or nothing runs. `bin/omamobile` restricts `UFS_RW` to
`boot_b init_boot_b vendor_boot_b vendor_kernel_boot_b dtbo_b userdata`
(line 133), refuses android-v0/qcom-abl for `flash`/`push`, finds slots by
GPT `PARTNAME`, checks `ro`, size, and AVB footer exactness before any
write. `packages/omamobile-boot-update` refuses unless slot B is the
booting slot (bootconfig AND cmdline), the initramfs allowlist equals the
descriptor's, and writes are verified by leading-bytes sha256 read-back
with the previous images kept for `rollback`.

Layer 2 — **descriptors are data.** 10+ consumers parse `device.conf`
with the same invariant (no `$`, backtick, backslash, quotes, control
chars; nothing sourced). Verified in `install-phone:117-135`,
`bin/omamobile:132-145`, `omamobile-firstboot:91-113`, `nv-backup:115`.

Layer 3 — **the phone enforces it too.** `initramfs/init:47-170`: the
allowlist is baked into the image; for guarded disks the whole-disk node
is *removed*; every other partition gets `blockdev --setro` with a retry
and a `.failed` marker; `ufs_unguarded` reports anything left writable.
Malformed/missing allowlist ⇒ everything read-only (fail closed).

Layer 4 — **dead men hold the doors.** `initramfs/init:397-415`: no USB
host configured within 45 s → on-screen dmesg → 20 s grace (held during
root-resize) → `panic=10` → ABL exhausts slot-B retries → slot A (stock
Android) boots. `tools/usbc-deadman` + CONTRIBUTING §3.4 codify the
pattern for risky steps; `tools/nv-backup` refuses anything not
read-only, unmounted, COMPATIBLE-matched.

Layer 5 — **integrity chain.** Bundle: `SHA256SUMS.sig` verified against
hardcoded fingerprints (`SIGNING_KEYS`, `install-phone:51`) in an isolated
GNUPGHOME; `manifest.json` (parsed by `python3 -I` with strict types and
regexes) must equal the descriptor's allowlist, exact write list, sizes
and order; the root image must match the signed manifest's digest;
confirmation requires typing the codename. Key hygiene: `omamobile.gpg`
is public-only (0 secret packets, verified with `gpg --list-packets`);
`release-key-init` makes an offline cert-only primary + online subkey with
a documented revoke-and-rotate path.

## 4. Findings

Severity rationale uses access/effect: anything requiring the phone in
hand, root on the build host, or the maintainer's own machine cannot be
High; the pipeline's most valuable asset is the trust chain of a release.

**S-1 — Low — CI hygiene.** `.github/workflows/checks.yml:27,61` pin
`actions/checkout@v5` by tag (mutable); `:46` uses `container:
archlinux:latest`; `:38-41` conditionally installs an unpinned
`archive.archlinux.org` package. `permissions: contents: read`, no
secrets, `pull_request` (never `pull_request_target`) — so the ceiling is
"attacker code runs read-only in CI". Fix prepared: branch
`audit/pin-ci-checkout` (checkout @ `08c6903cd8c0fde910a37f88322edcfb5dd907a8`,
v5.0.0); also digest-pin the container.

**S-2 — Medium-Low — factory image integrity optional.** The factory zip
is the source of every blob `tools/phone-provision` pushes to the phone;
its only check is the `require board=` line inside the zip
(`extract-vendor-firmware:319`), and backup tars accept a missing
`.sha256` with a note (`phone-provision:268`). A tampered download passes
and its firmware lands on the phone. Fix prepared: branch
`audit/factory-zip-verify` adds `--expect-sha256 <digest Google
publishes>` — refusal proven end-to-end (`proof/phone-provision-sha.sh`:
wrong/malformed refuse, correct proceeds to the next gate, nothing
staged).

**S-3 — Low — SSH server-auth is opt-in.** `tools/phone-ssh:41,140`:
without `OMAMOBILE_SSH_KNOWN_HOSTS` every connection is
`StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null`. Client auth is
key-based, but `bin/omamobile push` streams slot-B images over this
channel; a bus-level MITM could alter them. Documented behavior
(CONTRIBUTING:164), USB-only threat model. Fix: default to a persisted
per-user known_hosts (TOFU once, strict after; keep the escape hatch for
the native-Linux/recovery key change).

**S-4 — Info — AVB test key.** `packages/omamobile-boot-update/avb` ships
AOSP's public `testkey_rsa4096.pem` and the hook refuses any other key
(`omamobile-boot-update:342`). Bootloader must be unlocked anyway, vbmeta
is never touched, so the footer asserts nothing — deliberate, worth one
paragraph in SECURITY-PLAN.

**S-5 — Info — in-bundle trust is self-referential.** The running
`install` verifies the bundle containing itself. Standard for
self-contained installers; mitigated by the download channel and by the
web-flasher/desktop-installer path consuming `manifest.json` as data.

**S-6 — Info — `bin/omamobile:876`.** `rm -rf "$img"/*`: safe by
construction (`$img` always ends `/images`), suggest `rm -rf -- "${img:?}"/*`.

**S-7 — Low — unrestricted /dev/mem.** `kernel/configs/omamobile.config`:
`CONFIG_DEVMEM=y`, `# CONFIG_STRICT_DEVMEM is not set`. Root on the phone
can map arbitrary physical memory; the bring-up probes (`tools/devmem.c`,
AoC/Cirrus tooling) explain it. Recommend `STRICT_DEVMEM=y` for release
kernels or documenting the trade-off.

**S-8 — Low — path confusion in phone-provision.** `tools/phone-provision:107`
cds to the repo root before arg checks, so a *relative* FACTORY.zip
resolves against the repository root: "no factory.zip" in the common case,
or a silently different file if a same-named file sits there. Fix: capture
`$PWD` before the `cd` and resolve user-supplied paths against it.

**Rejected finding (kept as a regression note).** `omamobile-firstboot`
`s_user` (lines 259/261) expands `${C[FULL_NAME]:+-c "${C[FULL_NAME]}"}`
unquoted. Looked like flag injection; is not: bash treats the inner-quoted
expansion as one field, quotes from the *value* are data
(`proof/useradd-argv-repro.sh`). The repo's own test line 163 matches real
argv. Do not "fix" it into string-concatenation.

## 8. UNVERIFIED — the hardware hand-off (needs a Pixel 7 Pro)

Ordered so the read-only paths are exercised before any write:

1. **Provisioning (read-only first):** `tools/nv-backup DIR` on a real
   phone — seven partitions (incl. `devinfo`), RO + unmounted checks,
   read-back compare, `SHA256SUMS`. Then `tools/phone-provision
   --first-install --nv-backup DIR FACTORY.zip` with `--expect-sha256`
   set to Google's published digest (S-2 branch), and without it, to
   observe today's silent path.
2. **Guard runtime:** after install, `cat /sys/block/sd*/ro`,
   `ufs_unguarded` equivalent empty, sda node absent, `*_b` + userdata
   writable, persist/efs/modem unwritable even as root-by-accident.
3. **Firstboot e2e:** user created from firstboot.conf, keyring init,
   ufw USB-only, SDDM autologin → lock, conf deleted (0600 throughout).
4. **Kernel update parity:** `omamobile-boot-update` hook vs the
   installer's ramdisk append (`tests/install-phone-initramfs` byte
   parity), rollback path from a deliberately bad image.
5. **Dead-man timing:** UDC crash at ~45 s + 20 s, `panic=10` fallback to
   slot A with stock intact; `usbc-deadman` undo on a fresh connection.
6. **Extraction on real images:** sparse vendor.img, super.img/EROFS
   paths, `require board=` behavior on a wrong-device zip.
